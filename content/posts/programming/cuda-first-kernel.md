## 先写一道题，让 CPU 来做

题目挑最简单的：**每个元素加 1**。

```text
b[i] = a[i] + 1
```

数组长度 6710 万个 float（2 的 26 次方），单个数组大约 268 MB（256 MiB）。

这就是一段普通得不能再普通的 C++（`malloc` / `free` 是 C 标准库的函数，C++ 把整套 C 库原封不动继承了，`<cstdlib>` 里就有；这里特意用它，是因为显卡那边的 `cudaMalloc` 长得跟它一模一样，两边好对照）：

```cpp
#include <cstdio>
#include <cstdlib>
#include <chrono>

const int N = 1 << 26;          // 6710 万个数

int main() {
    size_t bytes = sizeof(float) * N;

    float *a = (float *)malloc(bytes);
    float *b = (float *)malloc(bytes);
    for (int i = 0; i < N; ++i) a[i] = (float)i / N;

    // 热身：b 现在只是一张"虚拟地址"的凭据，物理内存一页都还没给
    // 第一次写入时内核才现场分页，这笔操作系统开销不该算进加法
    // （a 在上面初始化时已经写过一遍了，所以只需补 b 这一遍）
    for (int i = 0; i < N; ++i) b[i] = a[i] + 1.0f;

    auto t0 = std::chrono::high_resolution_clock::now();

    // 正片：计时从上面 t0 才开始，这一遍才是要报的数
    for (int i = 0; i < N; ++i) b[i] = a[i] + 1.0f;

    auto t1 = std::chrono::high_resolution_clock::now();
    double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();

    double sum = 0;
    for (int i = 0; i < N; ++i) sum += b[i];

    printf("CPU  %.2f ms  checksum = %.4f\n", ms, sum);
    free(a); free(b);
    return 0;
}
```

跑出来是这样：

```text
CPU  37.86 ms  checksum = 100663295.5000
```

四十毫秒上下，6710 万次加法。单核跑，一个 for 循环从头到尾。

（这几个数会飘，同一台机器换个时刻跑差 20% 很正常，看量级和比例，别抠末位。计时前两边都空跑过一遍热身——`malloc` 出来的 268 MB 第一次写入，系统要现场分配物理页，那笔开销属于操作系统，不该算进计算。去掉热身那一遍，这个数会直接涨到一百毫秒以上。）

注意那个 `checksum`，它是后面用来对答案的。GPU 算出来必须和它一样，否则就是算错了——这一点很关键，后面会讲到为什么。

## CUDA 到底给 C++ 加了什么

CUDA 不是一门新语言。

写的还是 C++——同一个 `for`，同一个 `if`，同一个 `b[i] = ...`。CUDA 提供的是一个编译器（`nvcc`）加一套运行库，让你能把**一部分函数**编译成显卡能执行的代码，再从主机侧去调用它。

所以它往 C++ 里加的东西，少得有点让人失望：

| 多出来的东西 | 作用 | 一眼记住 |
|---|---|---|
| `__global__` | 告诉编译器：这个函数要在显卡上跑 | kernel 的标记 |
| `<<<blocks, threads>>>` | 告诉显卡：开多少个线程来跑 | 尖括号是「启动配置」 |
| `cudaMalloc` / `cudaFree` | 在显存里要一块地 | 和 `malloc` 一个意思，只是地皮在显卡上 |
| `cudaMemcpy` | 数据在内存和显存之间搬 | 两种「内存」不互通，必须自己搬 |

就这四样。把上面那道题交给显卡，代码长这样：

```cpp
#include <cstdio>
#include <cstdlib>
#include <cuda_runtime.h>

const int N = 1 << 26;          // 和 CPU 版一模一样的规模

// 这个函数会在显卡上跑，每个线程负责一个下标
__global__ void compute(const float *a, float *b, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) b[i] = a[i] + 1.0f;
}

int main() {
    size_t bytes = sizeof(float) * N;

    float *h_a = (float *)malloc(bytes);   // 主机内存
    float *h_b = (float *)malloc(bytes);
    for (int i = 0; i < N; ++i) h_a[i] = (float)i / N;

    float *d_a = nullptr, *d_b = nullptr;  // 显存
    cudaMalloc(&d_a, bytes);
    cudaMalloc(&d_b, bytes);

    // 一个 block 开 256 个线程，算算一共要开多少个 block
    int threads = 256;
    int blocks = (N + threads - 1) / threads;

    // 搬进去 → 算 → 搬回来，就这三步
    cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice);
    compute<<<blocks, threads>>>(d_a, d_b, N);
    cudaMemcpy(h_b, d_b, bytes, cudaMemcpyDeviceToHost);

    double sum = 0;
    for (int i = 0; i < N; ++i) sum += h_b[i];

    printf("GPU  checksum = %.4f\n", sum);
    printf("     blocks = %d, threads = %d\n", blocks, threads);

    cudaFree(d_a); cudaFree(d_b);
    free(h_a); free(h_b);
    return 0;
}
```

对比着看，CPU 版和 GPU 版的骨架是同一个：分配内存 → 填数据 → 算 → 求和打印。真正多出来的就是表里那四样，语法一个没变。

（实测时我在三段各插了一对 `cudaEvent` 记时点，还先空跑了一遍热身；上面这版把记时和热身都拿掉了，免得喧宾夺主。）

跑起来：

```text
GPU  checksum = 100663295.5000
     blocks = 262144, threads = 256
```

校验和两边**一模一样，一个数都没差**。因为这道题是纯加法，没有浮点误差可飘——换成带 `sin` 的式子就不一定了，那是后话。

## 那行尖括号到底在说什么

先说清一个词。代码里那个带 `__global__` 的 `compute(...)`，正式叫法是 **kernel**（核函数）——CUDA 里「在显卡上跑的函数」。

但别把它想成「一个线程跑一次的函数」，正好相反：**kernel 是一段代码，显卡上的每个线程都要把它完整执行一遍**。所以你写 `int i = ...` 那行时，写的其实是「某一个线程怎么算出自己的编号」。

它和普通 C++ 函数差在三处：

| | 普通 C++ 函数 | kernel |
|---|---|---|
| 谁执行 | 调用它的那个线程，执行一次 | 成千上万个线程，各自执行一次 |
| 怎么调用 | `compute(a, b, n)` | `compute<<<blocks, threads>>>(a, b, n)` |
| 有没有返回值 | 想返回什么返回什么 | **只能是 `void`** |

最后一条值得多说一句：返回值被砍掉之后，结果就只能写进参数里的指针（`b`），再由 `cudaMemcpy` 搬回主机——这就是为什么 kernel 的参数里总有一两个指针是「用来装结果的」。

还有一个容易犯迷糊的地方：**这个 kernel 和操作系统的「内核」只是英文撞了词**。操作系统的 kernel 管进程、内存、驱动；CUDA 的 kernel 就是一段在显卡上跑的函数，中文一般译成「核函数」。

另外，kernel 和线程不是一回事：kernel 是那段代码，线程是执行它的工人；同一个 kernel 由几万个线程各跑一遍，每个线程算一个 `i`。

CPU 版里，循环是一个人从头干到尾：

```text
i = 0, 1, 2, 3, ..., 67108863     ← 一个线程，全干
```

GPU 版里这个循环不见了，变成开几万个线程、每个线程只算一个 `i`。循环没被消灭——它从「一个线程跑 6710 万遍」变成了「6710 万个线程各跑一遍」，摊给了硬件。

```text
线程 0     → 算 b[0]
线程 1     → 算 b[1]
线程 2     → 算 b[2]
...
线程 67108863 → 算 b[67108863]
```

每个线程怎么知道自己是第几号？靠 kernel 里这一行：

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
```

显卡上的线程是分层的，不是一大坨：

- 线程被分组成 block（线程块），block 再排成 grid（网格）
- `threadIdx.x` —— 我是这个 block 里的第几个线程（0 ~ 255）
- `blockDim.x` —— 一个 block 里有几个线程（本例 256）
- `blockIdx.x` —— 我是第几个 block（0 ~ 262143）

所以 `blockIdx.x * blockDim.x + threadIdx.x` 就是「前面所有 block 的人数加起来，再加上我在本 block 里的位置」——**全局唯一编号**。

用本例的数字对一遍：

| 量 | 值 | 含义 |
|---|---|---|
| `threads`（即 `blockDim.x`） | 256 | 一个 block 256 个线程 |
| `blocks`（即 grid 大小） | 262144 | 一共开了 26 万个 block |
| 总线程数 | 262144 × 256 = **67,108,864** | 正好等于 N |

一个线程一个下标，一个不多一个不少。

那 `if (i < n)` 是干嘛的？

因为 `blocks = (N + threads - 1) / threads` 是**向上取整**。N 能被 256 整除时刚好，不能整除时就会多开一点：

```text
N = 1000, threads = 256
blocks = (1000 + 255) / 256 = 4
总线程 = 4 × 256 = 1024  →  多出来 24 个线程（i = 1000..1023）
```

这 24 个线程没有对应的数据，如果不管它们，`b[1000]` 就会越界写坏别人的内存。所以必须加一句 `if (i < n)` 把它们拦住。

这个 `if` 不能省。忘了它，程序可能在 N 正好整除时一切正常，换个 N 就悄悄越界——这类 bug 极难查。

## CPU 和 GPU，到底差在哪

先看硬件。我这台机器的两组数据：

| | CPU | GPU |
|---|---|---|
| 能同时干活的单元 | 16 个逻辑核 | 26 个 SM，每个 SM 128 个算术单元，约 **3328 个** |
| 单个单元的水平 | 强：能预测分支、乱序执行、缓存大 | 弱：只会老实算，遇到分支还得排队 |
| 内存带宽 | 几十 GB/s（DDR5） | **384 GB/s**（GDDR7，128 bit × 24 Gbps） |

用人的比方说：CPU 是十几个博士生，什么都会，但一次只能专心做一件事；GPU 是三千多个小学生，只会加减乘除，但可以同时开工。

这道题是 6710 万次「加 1」，每道都一样——这种活小学生赢。

再往下看一层，差别其实在两边设计时的假设。

CPU 的前提是「我不知道下一步要算什么」——所以它把芯片面积大量花在预测、重排、缓存上，遇到分支和随机访问也不至于停下来等。代价是算术单元少：它最宽的 **SIMD**（单指令多数据）指令一次也就喂 8 个 float（AVX2），和显卡 3328 个单元同时开工不是一个量级。

GPU 的前提正好相反：「我知道接下来几万个线程要做完全一样的事」。所以它把面积几乎全给了算术单元，一条指令同时喂给 32 个线程（这叫 **SIMT**，单指令多线程）。代价是：**只要线程之间开始走不同的路，效率立刻掉。**

具体点说，kernel 里写一句：

```cpp
if (a[i] > 0) b[i] = 1.0f;
else          b[i] = 2.0f;
```

如果这 32 个线程里有 20 个走 `if`、12 个走 `else`，显卡不会「两边同时干」，而是先让 20 个干、另外 12 个干等着，再反过来一次。总时间等于两边相加，等于白瞎一半算力。CPU 这边同样的情况反而没事，它本来就有分支预测在伺候。

所以一件事该不该交给显卡，第一道关是「能不能拆」：

- 每项都能独立算（`b[i] = a[i] + 1`，6710 万次互不相干）→ 有资格上 GPU
- 第 i 步必须等第 i-1 步的结果（排序、递归、状态机）→ 拆不开，硬写只会更慢

但有资格不等于划算。还有第二道关：每份工作够不够重。这一关得用数字说话。

## SIMD 和 SIMT，名字只差一个字母

上一节顺手带过了两个名字：CPU 那边的 **SIMD**，显卡这边的 **SIMT**。先把这两个词本身拆开。

- **SIMD = Single Instruction, Multiple Data**，一条指令，多份数据。
- **SIMT = Single Instruction, Multiple Threads**，一条指令，多个线程。

两个名字只差最后那个词，前面三个词一模一样——说明它们是同一个念头的两个版本。

为什么会有这个念头？CPU 执行一条加法指令，本来是：取一个数、取另一个数、相加、放回去。这条指令的代价不在「加」上，而在取指、译码那一整套流程上，走完才出一个结果。算术单元在旁边干等，等的过程全是浪费。既然取指译码的钱已经花定了，那就一次多喂几个数据进去。

这不是显卡的首创。机器在很早之前按「一条指令管几份数据」分成了四类：

| 类别 | 一条指令管几份数据 | 身边的例子 |
|---|---|---|
| SISD | 1 份 | 最普通的那行 `b[i] = a[i] + 1` |
| SIMD | 多份，通常 4～16 份 | x86 的 SSE / AVX，手机 ARM 里的 NEON |
| MISD | 多条指令算同一份数据 | 基本只停在教科书和容错系统里 |
| MIMD | 多条指令算多份数据 | 多核 CPU、一个集群 |

SIMD 就是表里第二行。表里还有个 MIMD——**多核 CPU 就是 MIMD**，每个核跑自己的一整套指令，互不相干。那显卡为什么不干脆做一堆核，反而要另立门户？

因为 **SIMT 不在这张表里**。它是 NVIDIA 在 2006 年造的词，卡在 SIMD 和 MIMD 中间：**硬件上是 SIMD**（32 个算术单元共享一条指令），**编程上像 MIMD**（每个线程有自己的寄存器、自己的下标，看着像各跑各的程序）。AMD 那边同类的东西叫 wavefront，一条管 64 个线程。

两个模型各自的形象：

- SIMD 是一个工人拿着一把 8 齿的叉子，一叉下去 8 块肉，但 8 块肉必须绑在一起；
- SIMT 是 32 个工人各拿各的叉子，听同一个口令，口令一响同时叉，谁手里有肉谁自己管。

SIMD 的长相是把数据打包塞进一个宽寄存器：

```text
[ a0 a1 a2 a3 a4 a5 a6 a7 ]   ← 一个 256 位寄存器
[ b0 b1 b2 b3 b4 b5 b6 b7 ]   ← 一个 256 位寄存器
                ↓ 一条加法指令
[ c0 c1 c2 c3 c4 c5 c6 c7 ]   ← 8 个结果，一次出
```

所以在 AVX2 这种指令集下，一个核一次能出 8 个结果，而不是 1 个（AVX-512 是 16 个）。我们上面那个 `b[i] = a[i] + 1` 的循环，编译器基本会自动帮你改写成这种形式——**你一行 CUDA 没写，CPU 早就在并行干活了**，只不过它的宽度被硅片焊死了，最多 8 个。

这个「一次算一个」改写成「一次算一批」的动作，叫 **向量化**（vectorization）。

具体长这样。先看标量写法，也就是不向量化的版本：

```cpp
for (int i = 0; i < 8; ++i) c[i] = a[i] + b[i];   // 8 次加法
```

向量化之后，机器上真正跑的更接近：

```text
load   a[0..7]     ← 一条指令搬 8 个
load   b[0..7]     ← 一条指令搬 8 个
vaddps             ← 一条指令加 8 个
store  c[0..7]     ← 一条指令存 8 个
```

一条 `vaddps` 就把 8 次加法全包了——原来得老老实实发 8 条加法指令。这件事可以编译器自动做（叫自动向量化），也可以人手动写——编译器认不出来的时候，就得自己把循环拆成这种形式。

「向量」这个词容易误会：它在这里是一串数的意思，跟数学里那个有方向的向量没有半点关系，纯属中文译名撞车。

编译器要敢这么改，得先证明这 8 次循环互不打扰——`c[i]` 的写入不能影响 `a[j]` 的读取。一旦它怀疑 `a` 和 `c` 可能是同一块内存，就只能老老实实一次算一个。所以能不能向量化，最后取决于同一件事：

- 数据彼此独立（`c[i] = a[i] + b[i]`）→ 编译器敢改，显卡也敢并行
- 有前后依赖（`a[i] = a[i-1] + 1`）→ 两边都不敢

这条和前面「能不能拆」是同一道关。

SIMT 则把「8 个槽位」换成「32 个线程」：

```text
线程 0    线程 1    线程 2   ...   线程 31      ← 一个 warp
  i=0       i=1       i=2    ...     i=31
                     ↓ 一条加法指令
b[0]+1    b[1]+1    b[2]+1   ...   b[31]+1      ← 32 个结果，一次出
```

看着只差在数字上（8 → 32），但本质不一样：

| | SIMD（CPU） | SIMT（GPU） |
|---|---|---|
| 一条指令作用于 | 一个宽寄存器里的 8 个槽 | 32 个线程（一个 warp） |
| 每份数据有「自己的」存储吗 | 没有，只是同一个寄存器里的第 k 个槽 | 有，每个线程有自己的寄存器和自己的 `i` |
| 宽度 | 8（AVX2）/ 16（AVX-512） | 32（AMD 那边是 64） |
| 谁负责凑够那 8 个 / 32 个 | 编译器自动向量化，或者人手动写 | 硬件按 `threadIdx` 自动捆 |
| 写代码时想什么 | 「怎么让编译器认出这是向量」 | 「一个线程算一个元素」 |

最后两行是关键。SIMD 里那 8 个槽是**同一份数据的不同元素**，共享一个寄存器名；SIMT 里 32 个线程各过各的日子，只是碰巧同步走着同一条指令。正因为如此，显卡的代码才好写——你只管安排「线程 i 算 b[i]」，捆成 warp、同一拍发射，是硬件的事。

两边都怕同一件事：这些数据走不同的路。

SIMD 遇到 `if`，编译器要么生成「两条路都算完再挑一个」，要么干脆放弃向量化，退回一次一个。SIMT 遇到 `if`，就是上一节说的 warp divergence：两条分支串行走，走不到的线程空转。

## 把加速比拆开看

有了这条宽度对比，可以把加速比拆开算算它从哪来。

| | 一条加法指令干几件事 | 算完 6710 万个元素要发多少条指令 |
|---|---|---|
| CPU（AVX2，单核） | 8 | 6710 万 ÷ 8 ≈ **839 万条** |
| GPU（一个 warp） | 32 | 6710 万 ÷ 32 ≈ **210 万条** |

4 倍。可 kernel 实测快了 22 倍，**多出来的 5 倍多不在「宽度」上，在「带宽」上。**

这道题几乎不计算，只是在搬东西：读 4 字节、写 4 字节，268 MB 的数据要过 536 MB 的流量。1.76 ms 搬完 536 MB，折算约 305 GB/s，差不多顶到这块显卡 384 GB/s 的上限。而 CPU 单核 37.86 ms 搬同样多，只有 14 GB/s 左右——**不是它算得慢，是一个核喂不饱内存。**

（CPU 当然不是没辙：开 16 个线程，每核再各自向量化，还能再快一个量级。但那要自己搭线程池、切任务、处理同步，显卡是把这些事直接做进硬件里了。）

或许后面可以再做一个更有意思的实验：让 CPU 开好多线程，每个核心尽可能利用 SIMD 向量化，再和 GPU 的大规模并行正面比一场速度。究竟谁更快？不同计算任务下，胜负又会不会反转？感觉这会是个很有意思的坑，值得后面专门折腾一下。

## kernel 快 22 倍，端到端输一半

把两边的耗时都测出来（各跑 15 次取中位数，下面同），并且把 GPU 的时间拆成三段：

| 阶段 | 耗时 | 折算速度 |
|---|---|---|
| CPU 一次算完 | 37.86 ms | — |
| **GPU kernel 本身** | **1.76 ms** | — |
| 主机 → 设备（搬 268 MB 进去） | 33.67 ms | 8.0 GB/s |
| 设备 → 主机（搬 268 MB 出来） | 42.17 ms | 6.4 GB/s |
| 其余（`cudaMalloc`、首次访问显存、同步） | 约 1.96 ms | 倒推的差额 |
| **GPU 算上搬数据的总时间** | **79.56 ms** | — |

三段加起来是 77.60，和端到端的 79.56 差 1.96 毫秒。这个差额我没能完全对上，怀疑是 `cudaMalloc` 和第一次访问显存的开销，但没有单独测过。

只看中间那一行（kernel）：**22 倍**。

算上两趟搬运：**0.48 倍**。

0.48 的意思是——显卡不但没有更快，**它慢了一倍**。

### 把题目加重：只改一行

显卡输，是因为这道题太轻。那把它改重，能不能看出显卡的本事？

改的只有一行：

```cpp
// 简单版
b[i] = a[i] + 1.0f;

// 复杂版
b[i] = sinf(a[i]) * sqrtf(a[i] + 1.0f);
```

CPU 版完整代码，只有 `#include <cmath>` 和那一行是新的：

```cpp
#include <cstdio>
#include <cstdlib>
#include <cmath>          // 新加的
#include <chrono>

const int N = 1 << 26;

int main() {
    size_t bytes = sizeof(float) * N;

    float *a = (float *)malloc(bytes);
    float *b = (float *)malloc(bytes);
    for (int i = 0; i < N; ++i) a[i] = (float)i / N;

    // 同样先热身一遍
    for (int i = 0; i < N; ++i) b[i] = sinf(a[i]) * sqrtf(a[i] + 1.0f);

    auto t0 = std::chrono::high_resolution_clock::now();

    // 正片：全部的计算就这一行
    for (int i = 0; i < N; ++i) b[i] = sinf(a[i]) * sqrtf(a[i] + 1.0f);

    auto t1 = std::chrono::high_resolution_clock::now();
    double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();

    double sum = 0;
    for (int i = 0; i < N; ++i) sum += b[i];

    printf("CPU  %.2f ms  checksum = %.4f\n", ms, sum);
    free(a); free(b);
    return 0;
}
```

```text
CPU  150.01 ms  checksum = 39581305.6365
```

37.86 → 150.01，时间涨了近四倍。它这次是真在算：6710 万次正弦、6710 万次开方，一次都省不掉。

GPU 版同样，只动 kernel 里那一行：

```cpp
#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <cuda_runtime.h>

const int N = 1 << 26;

__global__ void compute(const float *a, float *b, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) b[i] = sinf(a[i]) * sqrtf(a[i] + 1.0f);   // 只有这里变了
}

int main() {
    size_t bytes = sizeof(float) * N;

    float *h_a = (float *)malloc(bytes);
    float *h_b = (float *)malloc(bytes);
    for (int i = 0; i < N; ++i) h_a[i] = (float)i / N;

    float *d_a = nullptr, *d_b = nullptr;
    cudaMalloc(&d_a, bytes);
    cudaMalloc(&d_b, bytes);

    int threads = 256;
    int blocks = (N + threads - 1) / threads;

    cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice);
    compute<<<blocks, threads>>>(d_a, d_b, N);
    cudaMemcpy(h_b, d_b, bytes, cudaMemcpyDeviceToHost);

    double sum = 0;
    for (int i = 0; i < N; ++i) sum += h_b[i];

    printf("GPU  checksum = %.4f\n", sum);
    printf("     blocks = %d, threads = %d\n", blocks, threads);

    cudaFree(d_a); cudaFree(d_b);
    free(h_a); free(h_b);
    return 0;
}
```

```text
GPU  checksum = 39581306.4220
     blocks = 262144, threads = 256
```

两个版本摆在一起：

| | CPU | kernel | 端到端 | kernel 倍数 | 端到端 |
|---|---|---|---|---|---|
| 简单版 `a + 1` | 37.86 ms | 1.76 ms | 79.56 ms | 22× | **0.48×** |
| 复杂版 `sin × sqrt` | 150.01 ms | 1.76 ms | 76.52 ms | 85× | **1.96×** |

先看 kernel 那一列：1.76 和 1.76，一模一样。

这个结果我当时不太敢信——`sin` 加 `sqrt` 那么多活，怎么可能一点时间都不多花。能想到的解释是带宽：这段 kernel 读 268 MB、写 268 MB，合计 536 MB，1.76 毫秒搬完约合 305 GB/s，已经贴着这张卡 384 GB/s 的上限，多出来的算术大概全被埋进了等数据的时间里。

但这只是从数字倒推，我没做实验去证实。真要验证，得把数据先放进显存、反复算几十遍不搬运，看时间会不会跟着计算量涨——这个我还没做。

再看 CPU 那一列：涨了近四倍，因为它每一步都在算。

最后看端到端：79.56 和 76.52，几乎一样。因为 PCIe 这条管子每秒只过七八个 GB，题目重不重它都是这个速度。

搬运的成本基本不变，题目越重，显卡越划算。

简单版里算 1.76 毫秒、搬 76 毫秒，搬运占了九成以上；复杂版把 CPU 拖到 150 毫秒，GPU 的总时间却几乎没动，倍数就从 0.48 翻到了 1.96。

两个 checksum 差 0.78（`39581305.6365` 和 `39581306.4220`）：6710 万个浮点数相加，加法顺序一变，末尾几位就会飘。0.78 相对 3958 万大约是 2×10⁻⁸，比 float 本身的相对精度（约 1.2×10⁻⁷）还小一个量级，所以这个差是合理的。

不过 checksum 对得上，只能说明没有离谱地算错。真要验证，得逐元素比 CPU 和 GPU 的输出、看最大误差，或者用 double 累加一份参考值。这一步我还没做。

这也解释了网上那些「GPU 快 100 倍」「加速比 200 倍」是怎么来的——它们只报 kernel 那一行。你把数据搬过去、算完再搬回来，这两趟是不打折的。

> **GPU 不是「更快的 CPU」，它是「算力极强、但接了一条细水管」的机器。**
> 想让 GPU 划算，就得让「算」的收益盖过「搬」的成本：要么式子够重，要么同一份数据反复算很多遍。

## 小结

回头看，这一章主要说了这么几件事：

1. **CUDA 不是新语言**，它是给 C++ 加的四样东西（`__global__`、`<<<>>>`、`cudaMalloc`、`cudaMemcpy`）。语法门槛比想象中低。
2. **CPU 和 GPU 的差别不在快慢，在设计前提**。一个随时准备应付未知的下一步，一个专门重复同一件事几千遍。所以这个例子里看不到循环——6710 万次迭代被摊给了 6710 万个线程，GPU 当然也能写循环，只是这种题型用不上。
3. **加速比要连着搬运一起算**，而且**计算量太小时显卡会输**。第一道题它只有 CPU 的一半速度（0.48 倍）；同样是这份框架，只把式子加重到 `sin × sqrt`，就翻到了 1.96 倍。

说到底，CPU 擅长处理变化多的任务，GPU 擅长把大量相似的计算并行化。
